# Release Notes - v0.4.0

**Release Date:** 2026-11-21

## Overview

The first round of reports in the v0.3 format showed what the format could
not say. A release is a push and then a tag; a deploy is followed by a test
and a setting change; a push may apply only if the operator answers a
question one way; a secret is set by hand and must never appear in the
report. This release lets operator actions express those sequences, makes
every repeatable value a list, and lets a session find the role it plays
without being restarted.

**Breaking changes for Go callers:** an action's `Commit`, `PullRequest`
and `Version` become `Commits`, `PullRequests` and `Versions`; `Unblocks`
on actions and blockers and a blocker's `WaitingOn` become string slices.
Reports written in the v0.3 format still load.

## New Features

### Sequences of operator actions

```json
"operatorActions": [
  {"id": "push", "kind": "push", "description": "Push the coupon release.",
    "command": "git -C billing push origin main", "repository": "github.com/example/billing", "branch": "main"},
  {"kind": "tag", "description": "Tag the coupon release.", "after": ["push"],
    "versions": ["v1.4.0"], "irreversible": true, "followUp": "Record the release."},
  {"kind": "merge", "description": "Merge the stacking branch.", "decision": "coupon-stacking", "option": "stack-two"},
  {"kind": "configure", "description": "Set the webhook secret in production.",
    "steps": ["Copy the signing secret from the provider.", "Store it as /billing/prod/WEBHOOK_SECRET."],
    "credentials": ["billing/prod/WEBHOOK_SECRET"]}
]
```

- `id` and `after` order actions; validation rejects unknown IDs and cycles
- `decision` and `option` tie an action to an open decision request: the
  briefing marks it until the operator decides, then keeps it for that
  option and drops it for any other
- `steps` replace a single command for work by hand
- `credentials` name credential registry IDs, never values
- `ongoing` marks something kept up, such as a local webhook listener, and
  `followUp` says what the role does once the operator has acted

### Lists and states

- `commits`, `pullRequests`, `versions` and `unblocks` on actions, and
  `waitingOn` on blockers, are lists: a push covering several commits, a
  nested module's second tag on one commit, a blocker that waits on another
  role and then on the operator
- An `uncommitted` state for finished work waiting on review; work in
  progress carries its state, so committed but unpushed work is listed once
- Items carry `versions`; actions carry `paths`

### Session binding

```bash
plexushive -C my-hive start billing   # bind the role to this tmux session and print its context
plexushive -C my-hive context         # the same context, for a hook after start or compaction
plexushive whoami                     # the role and where it was found
```

Every command finds the role from `--role`, then `HIVE_ROLE`, then the tmux
session's environment, so an agent started before the binding still finds
it. `report submit` fills `session.tmux` inside tmux.

### Briefing

- A step several roles ask for is listed once with all their names: a push
  to the same repository and branch, or an action with the same kind,
  repository, branch and command
- A role whose only open work waits on its own decision requests shows as
  `decision`, neither idle nor blocked
- Actions show their versions, credentials, the actions they wait on,
  numbered steps and the role's follow-up

### Validation

- The schema carries the patterns validation applies: repositories,
  commits, pull requests, refs, credentials and role names
- A pull request may be given as `#<n>` when one repository is named; it is
  stored as the full URL
- `asked` accepts a date alone, though `report submit` sets it anyway

## Library

- `hive.ResolveRole`, `hive.BindTmuxRole`, `hive.TmuxSession`,
  `hive.TmuxRole`, `hive.InTmux` and the replaceable `hive.Tmux`
- `hive.NewContext`, `hive.Context` and `hive.Peer`
- `(*hive.Report).Normalize`; `hive.WriteReport` normalizes before it
  validates
- `hive.Decision.Option`, set by `Decide`
- `hive.RoleAction.Roles` and `Condition`, and `hive.Briefing.Waiting`
